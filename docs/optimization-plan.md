# GP 项目全面审计与优化方案

> 日期：2026-08-15 ｜ 状态：仅提出方案，未执行修改
> 规模：后端 Python ~12.6k 行（22 个路由模块）｜前端 TS/Vue ~10.9k 行｜数据库 2.3GB（1293 万行 K 线）

---

## 一、架构与稳定性（P0 最高优先）

### 1.1 定时任务与后端进程强耦合 ⚠️ 最严重
- **现状**：全部数据更新任务（15:30 K线增量 / 16:00 全市场同步 / 21:00 备份）都注册在 APScheduler 里，**运行在后端 uvicorn 进程内**。后端一停，所有任务失效（8-12~8-13 停机 47 小时错过两天数据的教训）。
- **方案**：
  - 关键任务独立成 launchd/cron（**选股信号推送已这么做**——`com.dsh.signal-push` 北京时间 15:35 独立触发 ✅）
  - 数据同步（`sync_watchlist`、全市场）也抽成独立脚本 + launchd，不依赖后端存活
  - 后端保留调度器作为补充，但不再作为唯一执行者

### 1.2 launchd 任务混乱（历史遗留）
- **现状**：曾同时加载 6 个相互冲突的后端拉起任务（端口冲突 + 数据库锁风暴，已卸载）；`com.gp.frontend` 仍加载但 PATH 错误（npm 在 `~/.hermes/node/bin`，plist 未配 → exit 127），前端实际靠会话后台任务在跑，**重启后前端会丢失**。
- **方案**：
  - 统一用一份带正确 PATH 的 plist 守护前端（`com.gp.frontend` 修正 PATH 后重载）
  - 后端用单一 launchd 任务守护（当前已卸载冲突项，补一个干净的）
  - 清理未用的 plist（`com.gp.services`、`ai.gp.*`、`service-daemon` 等备份）

### 1.3 数据库锁竞争
- **现状**：SQLite `journal_mode=delete`，后端 + 数据脚本 + 修复任务多进程写 → 反复出现 `database is locked`（本会话已遇到多次，靠杀进程解决）。
- **方案**：切换 **WAL 模式**（`PRAGMA journal_mode=WAL`），读写并发显著改善；所有连接统一 `busy_timeout=30s`（部分脚本已加，后端 `db.py` 需确认）。

## 二、数据与质量（P1）

### 2.1 复权数据层未使用
- **现状**：`kline_adjusted` 表 **0 行**；K 线 API 的 `adjust=qfq` 是查询时现算还是查空表？需确认复权链路是否正常。
- **方案**：验证 qfq 复权计算正确性（此前 volume/amount 修复会影响复权因子）；若查询时计算则保留，若依赖空表则补建。

### 2.2 数据源单点与健壮性
- **现状**：通达信依赖 `218.75.126.9` 单台服务器；东财接口有风控断连。
- **方案**：服务器列表配置化（可追加备用 IP）；数据源健康检查 + 自动降级（已有 mootdx→腾讯→新浪→百度 链路，可加告警）。

### 2.3 数据库膨胀与维护
- **现状**：2.3GB，含 1995 年至今全量；每日备份 2.4GB × 保留 7 份 ≈ 17GB 磁盘。
- **方案**：定期 `VACUUM`（删除后碎片）；备份策略可选保留周备份 + 月归档；老数据（如 2010 前）可选归档。

## 三、安全（P1）

### 3.1 鉴权关闭
- **现状**：`AUTH_ENABLED=false`，局域网内任何人可访问 GP（操作持仓/预警/备份下载 .db）。
- **方案**：开启鉴权（`AUTH_ENABLED=true` + 设置 AUTH_KEY），或至少限制端口访问（防火墙/Tailscale）。

### 3.2 Harness Web UI 暴露
- **现状**：DeepSeek Harness UI 只监听 `127.0.0.1`（安全），但如需远程访问（之前讨论过）必须走 SSH 隧道/Tailscale，**勿裸暴露公网**。

### 3.3 密钥管理
- **现状**：`NEWS_AI_API_KEY` 在 `.env`（已 gitignore ✅）；飞书 app secret 在 keychain ✅。
- **方案**：定期轮换密钥；.env 权限收紧（当前 600 ✅）。

## 四、代码与工程（P2）

### 4.1 零测试
- **现状**：项目 **0 个测试文件**（数据源解析、复权、因子计算、API 均无测试）。
- **方案**：优先为高风险逻辑加单元测试：
  - 数据源解析（sina/tencent/baidu/mootdx 字段解析）
  - 复权计算、`sync_service` upsert 逻辑
  - 因子计算（`scripts/v2/factors_v2.py`）与现有脚本回归
  - API 冒烟测试（health/watchlist/kline）

### 4.2 前端工程化
- **现状**：无 lint 脚本（仅 vue-tsc 类型检查）；无 CI。
- **方案**：加 `eslint` + `prettier`；可选 GitHub Actions 简单 CI（lint + 后端测试）。

### 4.3 生产部署模式
- **现状**：开发用 `vite dev` + uvicorn 直连；`nginx.conf`/Dockerfile 就绪但**未用于生产**。
- **方案**：前端 `vite build` + nginx 静态托管 + `/api` 反代（nginx.conf 已写好）；后端多 worker（uvicorn --workers）注意 SQLite 并发限制（建议保持单 worker + WAL）。

### 4.4 日志管理
- **现状**：`/tmp/gp-backend.err.log` 33MB 持续增长无轮转；`server.log` 旧日志残留。
- **方案**：日志轮转（macOS `newsyslog` 或 launchd 定时截断）；生产日志按天分文件。

## 五、性能（P2）

### 5.1 数据库查询
- **现状**：`kline_data` 1293 万行，有 `(stock_code, trade_date)` 唯一索引，kline 2500 根查询 ~50ms ✅ 健康。
- **方案**：无需优化；监控是否出现慢查询（大范围筛选接口 `screen` 全市场时注意）。

### 5.2 批量因子/同步脚本
- **现状**：全市场因子计算 ~75s、数据同步分钟级。
- **方案**：可选缓存中间结果（因子每日一算落盘）；同步加断点续跑（主板拉取脚本已有 ✅）。

## 六、业务与策略（P3）

### 6.1 选股 v2 接入 UI
- **现状**：v2 方案（脚本 + 飞书推送）已独立运行，但**未接入 GP 前端**。
- **方案**：新增 `screen_v2` API 返回当日信号，前端加选股面板（复用现有 screen 组件风格）。

### 6.2 预测模型重训
- **现状**：6 模型预测基于修复前的数据（volume/amount 修复影响特征输入）。
- **方案**：用修复后的数据重训/评估预测模型，确认准确率变化。

### 6.3 超跌因子库清理
- **现状**：29 个超跌因子有 3 个 quality=inferred（推断）和多个 low_sample，回测可信度存疑。
- **方案**：用修复后数据重跑 `train_factors.py` 回测，淘汰低样本/推断因子。

## 核心结论

1. **最该先做**：P0 的三件事——**关键任务脱离后端进程**、**launchd 统一守护**（否则重启后前端/后端会丢、定时任务再断档）、**数据库改 WAL**（消除锁风暴）。
2. **安全底线**：开启鉴权（当前局域网裸奔）。
3. **工程短板**：零测试是最大债务，核心解析逻辑应尽快补单测。
4. **项目亮点**（无需动）：数据库索引良好（查询 50ms）、数据源多级降级、备份自动运行、git 提交规范、选股 v2 已独立验证。
